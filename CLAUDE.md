## Проект

Веб-конфигуратор и дискретно-событийный симулятор процессов склада (по аналогии с GPSS World) —
React + TypeScript + Vite, чистый фронтенд без бэкенда. Пользователь строит 2D-план склада из
станций (ворота/сортировка/хранение/паллетирование/отгрузка и т.д.), соединяет их связями с
условиями маршрутизации, настраивает распределения времени/число людей/размеры партий — и
прогоняет симуляцию, смотрит анимацию и статистику.

Идея и данные выросли из двух реальных выгрузок WMS, которые пользователь приложил в начале
работы (`Схема склада.json` — топология физических ячеек, `Схема рекомендаций.json` — дерево
решений о размещении товара). **Важно**: это НЕ формат данных приложения — они использовались
как референс/источник для генератора сценария (см. «Импорт из выгрузки WMS» ниже), внутренняя
модель сценария полностью своя и проще.

Запуск: `npm run dev` (Vite, порт задаётся `--port`, у меня обычно 5199 — 8081 занят другим
проектом на этой машине). Тестов нет — верификация вручную через Browser pane + `tsc --noEmit` +
`npm run build`.

## Ключевые архитектурные решения

**Модель станции полностью generic** — один и тот же `Station.common` (`resourceCount`/
`serviceTime`/`batchIn`/`queueCapacity`) обслуживает ВСЕ 11 типов станций. Специфичное поведение
(разворот грузовика в единицы на воротах/приёме возвратов, назначение `destination` на сортировке,
объединение партии в 1 паллету/мобильный контейнер) — единственное место, `domain/behaviors.ts`,
свитч по `station.type`, все незнакомые/неспецифичные типы (включая `custom` — «своя станция» для
пользовательских процессов) падают в `default: return consumed` (простой passthrough). Отдельной
станции «упаковка» (pack) в модели НЕТ — товар упаковывается на сортировке, локальный товар идёт
из хранения сразу в мобильные контейнеры. Если добавляешь новый тип станции — в `behaviors.ts` НЕ
обязательно писать case, если поведение = passthrough.

**Маршрутизация — только рёбрами**, без встроенной в движок логики "куда дальше". Ребро имеет
`when: {flow?, sortType?, destination?, condition?, kind?}` — все заданные поля должны совпасть у
сущности, иначе ребро не подходит; среди подходящих рёбер — вес (`weight`). Если у станции для
сущности вообще нет подходящего ребра — сущность считается вышедшей из симуляции (exit), это
намеренное поведение (терминальные станции типа `shipTruck`/`utilization` не имеют исходящих
рёбер). **Ловушка**: если сгенерировать/собрать сценарий, где часть станций отсутствует, а
рёбра, ссылающиеся на них, остаются — сущности молча "теряются" (не крашится, просто не
досчитываются в статистике). См. `wmsImport.ts` — там из-за этого была реальная ошибка (backbone
топологии обязан быть ПОЛНЫМ, даже если под часть станций нет данных из реальных ячеек).

**`DEFAULT_EDGE_TEMPLATE`** (`domain/defaultScenario.ts`) — топология рёбер задана ТИПАМИ станций,
не id, и переиспользуется и дефолтным сценарием, и генератором из WMS-выгрузки
(`buildEdgesFromTemplate(typeToId)` пропускает рёбра, если одной из сторон нет в переданной
мапе). Меняешь топологию по умолчанию — правь только это место.

**Симуляция считается один раз целиком** (`engine/engine.ts:runSimulation`), не пошагово в
реальном времени — event-driven цикл с бинарной кучей по времени до `durationHours`, копит лог
переходов (`transitions`) и травел-сегментов (`travelSegments`, для анимации токенов между
станциями — записываются в момент `routeEntity`, а не постфактум). Плеер (`simStore.ts` +
`simview/SimPage.tsx#usePlaybackClock`) просто крутит `virtualTime` через requestAnimationFrame и
"прокручивает" уже готовый лог (`simview/liveState.ts` — бинарный поиск состояния станции/токенов
на момент `t`). Считается быстро (типовой прогон на 24ч — десятки-сотни мс), поэтому пересчёт при
каждом изменении параметра не проблема.

**`WarehouseCanvas.tsx` — общий SVG для конфигуратора и вьюера симуляции.** Зум/пан реализован
трансформом внутренней `<g transform="translate(x,y) scale(s)">`, а НЕ через
`preserveAspectRatio="none"` — **это специально**: SVG рендерится с дефолтным
`xMidYMid meet` (единый масштаб + леттербоксинг), и вся математика координат (`screenToViewport`/
`screenDeltaToViewport`/`viewportScale`) — точное обращение именно этого преобразования. Если
поставить `preserveAspectRatio="none"`, картинка перестаёт квадратно масштабироваться и
станции/текст визуально сплющиваются (уже наступал на эти грабли в сессии — не повторяй). Формула
проверена численно (соотношение сторон станции совпадает с точностью до 7 знаков после фикса).

Несколько рёбер между одной и той же парой станций рисуются НЕ поверх друг друга — есть
группировка по `(from,to)` и разведение дугой (`EDGE_SPACING`), с поправкой на то, что пик
квадратичной кривой Безье отклоняется от прямой только на половину смещения контрольной точки
(константа в 2 раза больше желаемого видимого зазора).

**Zustand-стор персистит ВСЁ состояние по умолчанию**, включая `selectedId` — после
`localStorage.removeItem('wh-modeling-scenario')` + `location.reload()` нужно ждать реального
маунта (persist пишет в storage только ПОСЛЕ первого `set()`, не сразу на инициализацию) — при
автоматизированной проверке в браузере учитывай это (иначе `localStorage.getItem(...)` сразу
после `reload()` вернёт `null`, хотя приложение уже отрисовалось).

**Библиотека прототипов станций** (`store/prototypeStore.ts`) — отдельный от сценария, глобально
персистящийся (свой ключ localStorage) каталог пользовательских шаблонов: имя + описание + цвет +
параметры. Прототип несёт КАТЕГОРИЮ (`PrototypeCategory`: входная/промежуточная/конечная) и конкретный
встроенный `type` станции (см. `STATION_CATEGORY`/`stationTypesOfCategory` в `domain/types.ts`).
Создание станции из прототипа рождает станцию РЕАЛЬНОГО типа (а не `custom`) с его специфичными
блоками `source`/`sort`/`returnsInspect` (доли входа/направлений/брака) — движок реально учитывает их.
Старые прототипы (без категории) мигрируют в `intermediate`/`custom` через persist-`migrate`
(`prototypeStore.ts`) — прежнее поведение «своя станция» сохраняется. `Station` получил опциональные
`color?`/`description?`, которые переопределяют `STATION_COLORS[type]`/`STATION_HINTS[type]` при
отрисовке и в панели параметров — заполняются при создании из прототипа, но дальше это обычные
редактируемые поля конкретного экземпляра (снапшот, без обратной связи с прототипом). Палитра
(`Palette.tsx`) группирует прототипы по категориям под встроенными типами и умеет СКРЫВАТЬ типы
станций из списка «Добавить станцию» (`hiddenStationTypes` в `scenarioStore`, охранная логика: тип
нельзя скрыть, если он применён на плане); создание/редактирование — `PrototypeEditorDialog.tsx`.

**Времена по видам предметов** — «матрицы тип ⨯ время» с фолбэком на общее значение. У ребра —
`travelTimeByKind?` (время переноса для каждого вида, фолбэк `travelTime`), у станции —
`common.serviceTimeByKind?` (время цикла для каждого вида, фолбэк `serviceTime`; цикл берёт партию,
вид — по ПЕРВОЙ сущности). В движке (`engine.ts`) время разрешается в `routeEntity`/`tryStart`; UI —
компонент `EntityKindTimeEditor.tsx` (используется в PropertyPanel и диалоге прототипов).

**SVG-текст в станциях обрезается вручную** (`WarehouseCanvas.tsx#truncateForWidth`) — `<text>` не
умеет переноситься/обрезаться сам, длинные названия (особенно из WMS-импорта, вида «Формирование
мобильных контейнеров (736 яч.)») иначе вылезали за рамку. Грубая оценка «символов на пиксель»
(не моноширинный шрифт, оценка не точная) + `clipPath` на станции как жёсткая страховка сверху.
Если начнёшь переделывать разметку станции — не убирай ни то, ни другое.

**Импорт из выгрузки WMS** (`domain/wmsImport.ts`) — генератор сценария из двух РЕАЛЬНЫХ файлов
WMS (не путать с обычным Импорт/Экспорт своего JSON-формата сценария в `App.tsx`, это отдельная
кнопка). Ключевая находка сессии: `Схема склада.json` (тысячи физических ячеек с тегами) реально
агрегируется по тегам в компактный набор станций — таблица `TAG_STATION_MAP` (порядок важен,
первый совпавший тег побеждает) + фолбэк по `subType`. А вот `Схема рекомендаций.json` оказалась
движком РАЗМЕЩЕНИЯ (какая ячейка/аллея/контейнер под товар), а НЕ маршрутизацией по этапам
процесса — ни один из 13 типов рекомендаций не говорит "уезжает грузовиком vs остаётся локально",
поэтому из него читаются только 2 узкие статистики (`analyzeRecommendations`): доля брака (ветки
`MoveToUtilizationCell`) и грубая оценка доли нонсорта (по `ArticleCategory`, эвристика без
реального обоснования в данных — так и подписано в UI). Ветка `IsTransitWarehouse` больше НЕ
трактуется как кросс-док — пользователь явно сказал «кросс-док не равен транзиту»; у входа доли
только «возвраты / сорт-груз / нонсорт» (`SourceParams.returnShare` + `nonsortShare`, остаток
прямого груза — сорт). Возвраты входят долей того же прямого потока (`sourceForward`), отдельного
источника возвратов `sourceReturn` в модели больше нет — возвратные машины уходят на `returnsGate`.
Пользователь ЯВНО отклонил вариант "завести новый атрибут категории предмета в движок,
чтобы связи реально фильтровались по ArticleCategory" — это осознанно НЕ сделано, было бы
несоразмерно большой работой ради 13 типов рекомендаций, которые всё равно про физическое
размещение, а не про канал отгрузки. Если попросят "сделать по-настоящему" — это большая
отдельная задача, планировать заново.
`parseLeadingJson` — реальный файл рекомендаций пользователя не парсится обычным `JSON.parse`
("Extra data" после основного документа), функция откусывает первый сбалансированный `{...}`.

## Известные пробелы / TODO

- Тестов нет вообще — верификация каждый раз вручную (`tsc --noEmit`, `npm run build`, ручные
  синтетические клики/pointer-события/drag через Browser pane, см. паттерны в истории сессии —
  ОБЯЗАТЕЛЬНО раздельными вызовами `javascript_exec` для pointerdown/pointermove/pointerup, иначе
  React-батчинг склеивает события в одном синхронном скрипте и состояние между ними не успевает
  закоммититься — ловил этот баг несколько раз, тратил время на ложные "баги").
- Bundle > 500kB (recharts тяжёлый) — vite ругается при сборке, не критично, но при желании можно
  code-split.
- `wmsImport.ts`: коэффициенты агрегации (`resourceCount = count/20` для не-storage типов) —
  грубая эвристика, открыто описана пользователю как "стартовая точка, дальше вручную". Таблица
  тегов НЕ исчерпывающая (покрывает ~30 самых частых/понятных тегов из реального файла, остальные
  ~20 редких/неоднозначных тегов игнорируются — попадают в fallback по subType).
- Нет zoom-to-fit / авто-раскладки при большом количестве станций (WMS-импорт кладёт станции в
  фиксированные "лейны", при ~11 станциях убористо, но помещается).
- `useSimStore.clear()` не чистит `history` (сравнение прогонов) — осознанно, чтобы можно было
  сравнивать прогоны ДО и ПОСЛЕ смены сценария целиком (в т.ч. после WMS-импорта).
